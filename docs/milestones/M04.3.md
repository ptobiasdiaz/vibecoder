## Arquitectura y autorización

`TaskExecutionService` conecta `PLANNED_WORK` de M04.2 con el worker M02 y los
adaptadores Git/GitHub existentes. La cadena verificable es:

`Issue → plan APPROVED → planned_task → Task → TaskExecutionWorkflow → sesión → commit → rama → PR`.

Solo es elegible una tarea materializada y pendiente de un proyecto `ACTIVE`. Se
verifican el hash y evento del plan, el especialista `ACTIVE`, su cuenta y la revisión,
configuración e instrucciones congeladas. El checkout de contexto se indica
explícitamente, debe estar limpio y corresponder al repositorio registrado.

La migración 0010 conserva autorización, agente/cuenta, workspace, base/rama, sesión,
hashes de contexto, resultado, validación, commit, push, PR, errores e intenciones
remotas. El worker solo admite la tarea si el workflow indicado está en `RUNNING`.

## Dependencias, workspace y sesión

Una dependencia solo está satisfecha cuando su workflow está `MERGED` después de
verificar el PR y su SHA. Cada tarea usa un clon confinado bajo el root configurado,
con rama `vibecoder/task-<uuid>` y SHA base congelado. No modifica el checkout del
desarrollador.

El contexto combina reglas globales/específicas, contexto aprobado, plan, tarea,
dependencias y rutas autorizadas, registrando hashes. La sesión de implementación es
exclusiva de la tarea; no se comparte con coordinación ni con otra tarea.

## Validación, commit y remoto

Se verifican cambios Git, rama/base, rutas, symlinks, tamaño, secretos y alcance.
`AGENTS.md`, `.vibecoder/` y `.git/` son sensibles. Un manifiesto SHA-256 impide
commitear cambios posteriores. Los comandos funcionales son argv sin shell, requieren
autorizador persistido y un segundo opt-in; por defecto no se ejecuta código generado.

El commit debe descender directamente de la base y es idempotente. Git usa `askpass`
temporal: el token no aparece en URL, argv ni configuración. No hay force push. El SHA
remoto se confirma y el PR usa marcador idempotente, con trazabilidad de Issue, plan,
tarea, agente, criterios, validaciones y commit. Nunca se hace merge automático.

## Recuperación

Un resultado Codex incierto no se reenvía. Un push incierto consulta la rama antes de
repetir; un PR con respuesta perdida se localiza por marcador/head/base. Se conservan
los workspaces. `reconcile` no repite inferencia ni validaciones funcionales a ciegas.

## CLI y pruebas

```bash
python -m vibecoder.tasks --database state.sqlite3 \
  --project-workspace /ruta/checkout-limpio \
  --workspace-root /ruta/workspaces-m043 --accounts accounts.json \
  eligible TASK_UUID

.venv/bin/python -m unittest tests.test_tasks -v
.venv/bin/python -m unittest discover -s tests -v
```

Comandos: `list`, `show`, `eligible`, `prepare`, `run`, `validate`, `commit`,
`publish`, `create-pr`, `check-merge`, `reconcile`, `inspect` y `errors`. Las escrituras
remotas exigen `--authorize-remote`.

`tests/test_tasks_live.py` separa preparación, Codex y escrituras GitHub con opt-ins
independientes; está desactivado por defecto.

## Limitaciones y aceptación

No hay scheduler, locks distribuidos, aislamiento fuerte para tests, supervisión de
reviews, correcciones ni cierre/merge automático. La implementación y pruebas offline
cubren autorización, workspace/sesión, validación, commit, publicación y PR
recuperables. El flujo live completo no se declara validado hasta ejecutarlo.
