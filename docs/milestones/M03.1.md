# M03.1 — Adaptador GitHub y registro de repositorios

Estado: **COMPLETADO; LECTURA LIVE VALIDADA**  
Fecha: 28 de octubre de 2026

## Objetivo y alcance

M03.1 conecta el núcleo persistente con GitHub REST API para registrar repositorios y
realizar operaciones explícitas sobre Issues, comentarios y etiquetas. No procesa
webhooks, no interpreta comandos, no ejecuta Codex y no modifica contenido Git.

## Dependencias

- `httpx >= 0.27, < 1`: transporte HTTP mantenido, timeouts, MockTransport y manejo
  explícito de errores de red.
- `pydantic >= 2.7, < 3`: valida los campos remotos utilizados y rechaza respuestas
  incompletas sin persistir payloads completos.

No se introduce framework web. Los reintentos son pequeños y propios: solo GET ante
errores de transporte o `502/503/504`; una escritura nunca se repite a ciegas.

## Arquitectura

```text
GitHubRegistryService -> GitHubClient (puerto) -> GitHubHttpClient -> GitHub REST
         |
         +-> OrchestratorCore / Repository -> SQLite
```

El servicio limita cada operación a un `GitHubRepository` registrado. El adaptador no
conoce proyectos ni SQLite. El contenido remoto se trata como datos no confiables y
no altera configuración ni dispara instrucciones.

## Autenticación y permisos

`GitHubConfig` recibe el token desde el proceso llamante. El token se oculta de la
representación de configuración y solo se usa en la cabecera `Authorization`; no se
guarda en SQLite, ficheros de configuración versionados ni mensajes de error.

La implementación inicial admite personal access tokens clásicos o fine-grained
configurados externamente. El puerto permite añadir después tokens de instalación de
GitHub App. Deben concederse solo metadatos/contenido de repositorio en lectura y,
cuando se usen escrituras, permisos de Issues en lectura/escritura.

`validate_identity()` comprueba `/user`; `validate_repository_access()` vuelve a leer
el repositorio y exige permiso `pull`, y opcionalmente `push`, `maintain` o `admin`.
GitHub puede no exponer scopes clásicos para todos los tipos de token, por lo que la
prueba efectiva del repositorio es la autoridad.

## Registro de repositorios

La migración `0003_github_repositories.sql` añade:

- `github_repositories`, uno por proyecto y único por `github_id`;
- metadatos actuales de propietario, nombre, URLs, rama por defecto opcional,
  visibilidad, archivado, permisos observados y fecha de sincronización;
- `github_operations`, con intención, clave idempotente, hash, estado y recurso remoto.

El ID numérico de GitHub es la identidad estable. Volver a registrar el mismo ID
actualiza propietario, nombre y URLs, permitiendo detectar renombrados. Un repositorio
vacío es válido: la consulta de commits interpreta el `409` documentado por GitHub
como repositorio sin commits y no exige rama, README ni contenido.

`Project.github_repository` se mantiene como nombre visible compatible con M01/M02;
la nueva entidad es la identidad autoritativa.

## Operaciones implementadas

- autenticar identidad;
- consultar, registrar y resincronizar repositorio;
- detectar repositorio vacío;
- listar y consultar Issues y su estado;
- crear Issues;
- listar y publicar comentarios;
- listar, consultar y crear etiquetas;
- reemplazar las etiquetas de un Issue.

Las listas siguen la paginación `Link` de GitHub. Las operaciones de escritura solo se
invocan mediante métodos explícitos.

## Idempotencia y recuperación

Antes de escribir se persiste `GitHubOperation(PENDING)` con una clave proporcionada
por el llamante y el hash canónico del payload. Reutilizar la clave con otro payload
se rechaza.

Issues y comentarios incluyen un marcador HTML derivado de la clave. Al repetir una
operación o reiniciar el proceso se listan los recursos remotos y se adopta el que ya
contenga el marcador. Las etiquetas se reconcilian por nombre y la asignación se
compara con el estado actual. Un fallo de transporte deja `UNKNOWN`; un rechazo HTTP
confirmado deja `FAILED`.

GitHub no garantiza idempotencia nativa general ni consistencia inmediata: existe una
ventana residual de duplicación si una escritura fue aceptada pero todavía no aparece
al reconciliar. No se afirma exactamente-una-vez.

## Errores

Se distinguen clases para autenticación (`401`), permisos (`403`), repositorio o
recurso inaccesible (`404`), rate limit (`429` o `403` con remaining cero), transporte
y `5xx`, errores permanentes y respuestas inválidas. No se clasifican errores usando
tokens ni se incluyen cabeceras sensibles.

## Configuración

Ejemplo programático, obteniendo el secreto del entorno:

```python
import os
from vibecoder.github import GitHubConfig, GitHubHttpClient

client = GitHubHttpClient(GitHubConfig(token=os.environ["VIBECODER_GITHUB_TOKEN"]))
service = GitHubRegistryService(core, client)
identity = service.validate_identity()
repository = service.register_repository(project.id, "owner", "repository")
service.validate_repository_access(repository.id, require_write=True)
```

El proceso responsable debe inyectar `VIBECODER_GITHUB_TOKEN`; no se proporciona ni
se lee automáticamente un archivo `.env`.

## Pruebas

Instalación y suite predeterminada, sin red ni credenciales:

```bash
.venv/bin/pip install -e .
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -v
```

Lectura live opcional:

```bash
M031_GITHUB_LIVE_READ=1 \
M031_GITHUB_TOKEN='token-externo' \
M031_GITHUB_REPOSITORY='owner/repo-de-pruebas' \
.venv/bin/python -m unittest tests.test_github_live.GitHubReadLiveTests -v
```

La prueba de escritura crea un Issue, comentario y etiqueta y solo debe ejecutarse en
un repositorio dedicado, con autorización expresa:

```bash
M031_GITHUB_LIVE_WRITE=I_UNDERSTAND_THIS_WRITES_TO_GITHUB \
M031_GITHUB_TOKEN='token-externo' \
M031_GITHUB_REPOSITORY='owner/repo-de-pruebas' \
.venv/bin/python -m unittest tests.test_github_live.GitHubWriteLiveTests -v
```

Ninguna prueba live se ejecuta por defecto.

## Criterios de aceptación

- [x] Adaptador desacoplado y autenticación externa.
- [x] Registro estable, detección de vacío, duplicados y renombrados.
- [x] Consulta y escrituras explícitas de Issues, comentarios y etiquetas.
- [x] Persistencia, integridad referencial y recuperación tras reinicio.
- [x] Clasificación de errores y validación de respuestas.
- [x] Idempotencia local/remota sin prometer exactamente-una-vez.
- [x] Pruebas predeterminadas sin red ni secretos.
- [x] Integraciones live separadas y desactivadas.

## Limitaciones

- solo tokens externos; GitHub App queda preparada por interfaz, no implementada;
- sin webhooks, polling automático ni procesamiento de comandos;
- no se almacenan ETags ni cursores incrementales;
- la reconciliación por listado puede ser costosa en repositorios con muchos Issues;
- no se implementan edición, cierre o borrado de Issues/comentarios/etiquetas;
- escritura live pendiente; la lectura fue validada contra
  `ptobiasdiaz/vibecoder_test`.
