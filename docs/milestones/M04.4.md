## Supervisión y polling

`PullRequestReviewService` se vincula uno-a-uno con un workflow M04.3. Consulta por
separado el PR, comentarios generales, reviews, comentarios de línea y commits. Cada
evento se deduplica por tipo e ID remoto; timestamps iguales no se usan como identidad
ni como causalidad entre endpoints.

La revisión efectiva considera únicamente la última review por autor para el HEAD
actual. Una aprobación de un commit anterior queda obsoleta. `closed` sin `merged` es
`CLOSED_UNMERGED`; una aprobación nunca equivale a merge.

## Identidad, enrutamiento y sesiones

Solo usuarios de la allowlist y no-bot pueden provocar conversación o corrección. Los
comentarios propios se reconocen mediante IDs de operaciones GitHub persistidas.
Comentarios técnicos se dirigen por defecto al especialista; `/agent main` y
`/agent <id>` son explícitos. Cada PR/agente conserva una sesión conversacional. Las
correcciones usan la sesión de implementación M04.3 y su workspace, nunca otra tarea.

## Alcance y autorización

La clasificación no se delega como autoridad a Codex. El operador registra
`IN_SCOPE`, `OUT_OF_SCOPE` o `AMBIGUOUS` y vincula eventos concretos. Solo `IN_SCOPE`
con autorización explícita crea `REVIEW_CORRECTION`; los demás estados se bloquean y
requieren aclaración o una nueva revisión aprobada del plan.

Antes de ejecutar se verifican proyecto, PR, agente, cuenta, revisión de configuración,
instrucciones, workspace, rama y SHA local/remoto. Una corrección activa impide otra
incompatible.

## Corrección, publicación y respuesta

La corrección pasa por `AUTHORIZED → RUNNING → GENERATED → VALIDATED → COMMITTED →
PUBLISHED → REPLIED`. Reutiliza LocalWorker, validaciones y Git seguro. Se protegen
`AGENTS.md`, `.vibecoder/`, secretos, symlinks, tamaños y rutas fuera de alcance. No se
ejecutan tests por defecto.

Se crea un commit descendiente del HEAD autorizado y se publica en la misma rama sin
force. No se crea otro PR. La respuesta se persiste antes de publicarse y solo afirma
que la corrección está pendiente de verificación humana.

## Merge y finalización

El merge requiere identidad/ramas correctas, `merged=true`, `merge_commit_sha` y que el
último SHA publicado figure entre los commits del PR. Esto admite merge commit, squash
y rebase sin exigir igualdad entre SHA publicado y SHA de merge. Se marcan supervisión
y ejecución como `MERGED`, haciendo elegibles las dependencias. No se ejecutan y el
Issue original permanece abierto.

## Recuperación y CLI

`reconcile` vuelve a consultar PR/rama, confirma pushes inciertos y reintenta únicamente
publicaciones cuya respuesta ya está persistida. Nunca repite inferencia. La CLI es:

```bash
python -m vibecoder.reviews --database state.sqlite3 \
  --project-workspace /ruta/proyecto --accounts accounts.json \
  --authorized-user usuario poll SUPERVISION_UUID
```

Comandos: `list`, `start`, `show`, `poll`, `events`, `process`, `corrections`,
`prepare-correction`, `run-correction`, `validate`, `commit`, `publish`, `reply`,
`check-merge`, `reconcile` y `errors`.

## Pruebas y limitaciones

Las pruebas offline usan Git/GitHub/Codex simulados. La prueba conjunta está en
`tests/test_reviews_live.py` y permanece opt-in. No hay webhooks, scheduler, locks,
merge, resolución automática de threads, replanificación autónoma, cierre de Issues
ni aislamiento fuerte para ejecutar código no confiable.
