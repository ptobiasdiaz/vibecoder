# M03.3.1 — Configuración Git negociada y aprobada

Estado: **COMPLETADO; FLUJO LIVE VALIDADO**  
Fecha: 29 de octubre de 2026

## Objetivo

M03.3.1 incorpora al bootstrap una configuración Git explícita, negociable y
versionada. La aprobación congela especificación, arquitectura, configuración y lista
exacta de operaciones remotas que M03.4 podrá considerar. Este hito no publica nada.

## Estado remoto y propuesta

Se captura ID estable GitHub, estado vacío, rama por defecto y SHA del HEAD. Para un
repositorio vacío se propone `main`, commit técnico mínimo, rama
`vibecoder/bootstrap-<workflow>`, PR y merge humano. Las operaciones futuras quedan
limitadas a `CREATE_TECHNICAL_BASE`, `PUBLISH_BOOTSTRAP_BRANCH` y
`CREATE_PULL_REQUEST`.

Con commits se conserva la rama por defecto, se guarda su HEAD, se usa `EXISTING_BASE`
y no se autoriza un commit técnico. Son propuestas modificables, no decisiones.

## Negociación estructurada

El principal recibe la revisión vigente, explica alternativas y no puede confirmarla.
El desarrollador modifica el JSON y publica exactamente un bloque:

````markdown
```vibecoder-git-config
{
  "schema_version": 1,
  "confirmation": "confirmed",
  "repository_id": "UUID-local",
  "main_branch": "main",
  "base_branch_exists": false,
  "initialization_strategy": "TECHNICAL_BASE_COMMIT",
  "technical_commit_policy": "CREATE_MINIMAL",
  "publication_policy": "PULL_REQUEST",
  "integration_policy": "HUMAN_REVIEW_MERGE",
  "bootstrap_branch": "vibecoder/bootstrap-12345678",
  "authorized_operations": [
    "CREATE_PULL_REQUEST",
    "CREATE_TECHNICAL_BASE",
    "PUBLISH_BOOTSTRAP_BRANCH"
  ]
}
```
````

El esquema es cerrado. Prosa, ejemplos, bloques duplicados, campos extra o
combinaciones incoherentes no confirman nada. El comentario de control no crea otra
tarea Codex.

La validación usa **Pydantic 2** (`pydantic>=2.7,<3`): aporta modelos tipados,
enumeraciones y rechazo de campos desconocidos sin introducir un framework web. La
persistencia continúa almacenando JSON canónico y campos auditables en SQLite, no
objetos dependientes de la biblioteca.

## Estados, hash y aprobación

```text
PROPOSED -> CONFIRMED -> APPROVED -> APPLIED
```

Cada modificación es una revisión. El hash SHA-256 usa JSON canónico sin estado ni
`confirmation`. `APPROVED` requiere la etiqueta y el evento humano verificable de
M03.2, y guarda el hash de la especificación congelada. Esta incluye el bloque
confirmado. Una configuración aprobada no admite cambios silenciosos.

`0006_git_configuration.sql` añade `git_configurations` y referencias opcionales en
`generation_workflows`. Un índice parcial impide dos configuraciones aprobadas por
workflow.

## Integración con M03.3

Una generación nueva exige configuración `APPROVED`/`APPLIED`, comprueba su hash de
especificación e identidad, usa exactamente su rama bootstrap y verifica al clonar:

- que un remoto vacío siga vacío;
- que rama por defecto y HEAD no hayan cambiado;
- que configuración y hash no cambien entre preparación y ejecución.

Después de preparar se marca `APPLIED`. Una discrepancia bloquea sin borrar el
workspace ni corregir GitHub.

Las generaciones anteriores conservan sus campos nullable, workspace y commit.
`legacy-check` informa que su aprobación histórica no autoriza efectos remotos M03.4;
una ampliación requiere un workflow humano nuevo.

## CLI

```bash
python3 -m vibecoder.bootstrap ... git-proposed PROJECT_ID
python3 -m vibecoder.bootstrap ... git-approved PROJECT_ID
python3 -m vibecoder.bootstrap ... git-validate PROJECT_ID --file CONFIG.md
python3 -m vibecoder.bootstrap ... git-check PROJECT_ID
python3 -m vibecoder.bootstrap ... git-operations PROJECT_ID
python3 -m vibecoder.generation ... legacy-check GENERATION_ID
```

`status` incluye propuesta y configuración aprobada. Los bloques se validan durante
polling; los errores aparecen en el diagnóstico normal de comentarios rechazados.

## Pruebas live opt-in

Lectura real, sin escritura:

```bash
M0331_LIVE=I_UNDERSTAND_THIS_MAY_WRITE_AN_ISSUE_COMMENT \
M0331_GITHUB_TOKEN="$VIBECODER_GITHUB_TOKEN" \
M0331_DATABASE="$VC_STATE_DIR/vibecoder.sqlite3" \
M0331_PROJECT_ID="$M032_PROJECT_ID" \
M0331_AUTHORIZED_USERS=ptobiasdiaz \
.venv/bin/python -m unittest \
  tests.test_git_config_live.GitConfigurationLiveTests.test_observe_real_repository_state -v
```

Publicar una propuesta requiere `M0331_STAGE=publish` y un workflow nuevo no aprobado.
Después del bloque humano y la etiqueta, la etapa `verify` comprueba persistencia y
compatibilidad. No debe reutilizarse retroactivamente el Issue ya congelado. Ninguna
etapa hace push, crea ramas remotas, commits remotos o Pull Requests.

### Resultado live observado

El 29 de octubre de 2026 se validó el flujo completo contra
`ptobiasdiaz/vibecoder_test` con un workflow nuevo: detección del remoto, publicación
de la propuesta, modificación y confirmación humana mediante el bloque estructurado,
atribución del evento `status:approved`, congelación conjunta y recuperación de la
configuración aprobada desde SQLite. La comprobación posterior confirmó que la
instantánea seguía siendo compatible con el repositorio remoto.

La prueba confirmó además que quitar una etiqueta no revoca un workflow ya congelado:
para no reescribir trazabilidad histórica fue necesario iniciar un workflow nuevo. No
se ejecutó Codex, no se publicó ninguna rama y no se creó ningún Pull Request.

## Limitaciones

- polling manual, sin webhooks;
- JSON estricto; no se infieren decisiones desde prosa;
- cualquier deriva requiere reconciliación humana;
- workflows históricos no reciben autorización retroactiva;
- no se implementan commit técnico remoto, push, PR ni merge;
- la publicación remota y su reconciliación pertenecen a M03.4.

## Criterios de aceptación

- [x] Propuestas distintas para remotos vacíos y existentes.
- [x] Modificación y confirmación humana estructurada.
- [x] Estados tipados, validación y hash reproducible.
- [x] Aprobación conjunta atribuible e inmutable.
- [x] Captura y comparación de identidad, rama y HEAD.
- [x] Consumo por M03.3 sin asumir `main`.
- [x] Preservación y diagnóstico de generaciones históricas.
- [x] Idempotencia, persistencia y aislamiento.
- [x] Pruebas predeterminadas sin GitHub ni Codex.
- [x] Validación live opt-in.
