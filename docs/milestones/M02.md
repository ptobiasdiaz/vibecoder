# M02 — Ejecución persistente de agentes Codex

Estado: **COMPLETADO**  
Versión contrastada: `codex-cli 0.163.0` (28 de octubre de 2026)

## Objetivo y alcance

M02 conecta el núcleo SQLite de M01 con Codex App Server mediante un worker local,
secuencial y recuperable. Ejecuta una tarea `PENDING` por invocación, mantiene sesiones
por agente/cuenta y persiste correlaciones y resultados sin depender de GitHub,
Telegram, FastAPI, Docker o una cola externa.

La descripción antigua del roadmap asignaba M02 al bootstrap GitHub. Este encargo es
la definición vigente; el bootstrap se difiere a M03 junto con su protocolo visible.

## Arquitectura

```text
CLI -> LocalWorker -> OrchestratorCore -> Repository/SQLite
          |
          +-> CodexAppServerExecutor -> AppServerClient -> codex app-server (stdio JSONL)
          |
          +-> AccountRuntimeConfig (JSON externo, sin secretos)
```

- `LocalWorker` selecciona y coordina; no implementa protocolo.
- `CodexAppServerExecutor` crea/reanuda threads, ejecuta turnos, reconcilia historial y
  garantiza el cierre del proceso.
- `AppServerClient`, validado en M00, conserva el transporte y dispatcher por turn ID.
- `OrchestratorCore` aplica transiciones y transacciones breves.
- Autenticación y secretos permanecen en el `CODEX_HOME` preparado por el operador.

## Ciclo de ejecución

1. Seleccionar la tarea `PENDING` más antigua. Estados de espera no se reintentan.
2. Resolver proyecto, agente, cuenta y configuración runtime.
3. Crear el intento y mover la tarea a `RUNNING` en una transacción.
4. Crear o recuperar la sesión y correlacionarla con el intento.
5. Arrancar App Server para la cuenta.
6. Reanudar el thread o crear uno nuevo y persistir su ID inmediatamente.
7. Iniciar el turno y persistir su ID antes de esperar la respuesta.
8. Esperar `turn/completed` sin mantener una transacción SQLite abierta.
9. Persistir estado final, texto final necesario para auditoría y error estructurado.
10. Cerrar App Server en `finally` y devolver el resultado del worker.

No se persisten deltas ni todos los eventos de streaming.

## Persistencia

La migración `0002_codex_execution.sql` añade:

- `tasks.prompt`;
- `execution_attempts.session_id`;
- `codex_thread_id` y `codex_turn_id`;
- `result_text`;
- estado de intento `CANCELLED`;
- índice de intentos por estado.

El intento existe antes de invocar Codex. Thread y turn se guardan en actualizaciones
independientes tan pronto como se conocen. El resultado siempre queda vinculado al
intento que lo produjo.

## Sesiones

- `NOT_CREATED`: no existe thread.
- `THREAD_CREATED_UNCONFIRMED`: existe ID, pero un thread vacío no es durable.
- `THREAD_PERSISTED`: terminó un primer turno.
- `RECOVERABLE`: puede reanudarse en otro proceso App Server.
- `UNAVAILABLE`/`LOST`: no debe sustituirse automáticamente fingiendo conservar contexto.

Un turno completado promociona una sesión nueva a `RECOVERABLE`. Un error inequívoco
al reanudar marca la sesión `LOST` y deja la tarea en espera conservadora.

## Estados y errores

La clasificación usa `turn.error.codexErrorInfo`, no coincidencias de texto:

| Señal | Tarea | Intento/cuenta |
|---|---|---|
| `completed` | `COMPLETED` | `SUCCEEDED` |
| `interrupted` | `CANCELLED` | `CANCELLED` |
| `Unauthorized` | `WAITING_AUTH` | `FAILED` / `AUTH_REQUIRED` |
| `UsageLimitExceeded` | `WAITING_QUOTA` | `FAILED` / `QUOTA_EXHAUSTED` |
| timeout | `WAITING` | `UNKNOWN` |
| transporte/App Server | `FAILED` | `FAILED` |
| fallo del agente no clasificado | `FAILED` | `FAILED` |

Los códigos desconocidos se conservan sin inventar una causa.

## Recuperación y reconciliación

`--recover` transforma intentos que quedaron `RUNNING` en `UNKNOWN` y sus tareas en
`WAITING`. No reenvía prompts.

Si se guardaron thread y turn, `--reconcile ATTEMPT_ID` consulta
`thread/turns/list`. Solo un estado final confirmado cambia el intento a
`SUCCEEDED`, `FAILED` o `CANCELLED`. Ausencia, estado activo o falta de IDs conserva
`UNKNOWN/WAITING`. Esta operación tampoco reenvía el prompt.

Reintentar una tarea con efectos externos requiere reconciliación o decisión humana.
Crear una nueva tarea puede ser seguro únicamente cuando el prompt sea idempotente o
se haya verificado que el intento anterior no produjo efectos.

## Configuración de cuentas

La base de datos guarda `credential_ref`, nunca credenciales. El JSON runtime, cuyo
ejemplo está en `examples/m02_accounts.example.json`, se indexa por ID de cuenta:

```json
{
  "accounts": {
    "ACCOUNT_UUID": {
      "codex_home": "/ruta/absoluta/codex-home-aislado",
      "codex_executable": "/ruta/absoluta/codex",
      "cwd": "/ruta/absoluta/workspace",
      "timeout_seconds": 600,
      "extra_args": []
    }
  }
}
```

El operador autentica previamente ese `CODEX_HOME`. El worker nunca ejecuta
`codex login`, copia credenciales ni rota cuentas.

## Ejecución

Crear una tarea ejecutable desde Python:

```python
task = core.create_task(
    project.id,
    agent.id,
    "CODEX",
    prompt="Analiza el repositorio y responde con un resumen breve.",
    idempotency_key="manual-001",
)
```

Después:

```bash
python3 -m vibecoder.worker --database ./vibecoder.sqlite3 \
  --accounts ./accounts.json --once
python3 -m vibecoder.worker --database ./vibecoder.sqlite3 --status
python3 -m vibecoder.worker --database ./vibecoder.sqlite3 --recover
python3 -m vibecoder.worker --database ./vibecoder.sqlite3 \
  --accounts ./accounts.json --reconcile ATTEMPT_ID
```

## Pruebas

Predeterminadas, sin credenciales ni inferencia:

```bash
python3 -m unittest discover -v
```

La integración live requiere activación explícita y consume cuota:

```bash
M02_CODEX_LIVE=1 \
M02_CODEX_HOME=/ruta/aislada/autenticada \
M02_CODEX_BIN=/ruta/a/codex \
python3 -m unittest tests.test_codex_executor.CodexExecutorLiveTests -v
```

No se copia automáticamente el home habitual.

### Validación live

El 28 de octubre de 2026 se ejecutaron las dos pruebas opt-in contra Codex App
Server real con un `CODEX_HOME` aislado y previamente autenticado:

```text
test_real_turn_and_resume ... ok
test_worker_persists_result_and_session_across_restart ... ok

Ran 2 tests in 6.567s

OK
```

La validación confirmó el flujo completo del worker: ejecución de un turno real,
persistencia del resultado y de los identificadores de thread/turn, cierre del
proceso App Server y reanudación de la misma sesión después de reiniciar tanto el
worker como App Server.

Durante la primera ejecución live se detectó que `thread/start.sandbox` recibía
`workspaceWrite`. Ese valor pertenece a una representación interna distinta y el
campo del protocolo espera `workspace-write` (o `read-only` / `danger-full-access`).
Se corrigió el adaptador, se centralizaron las enumeraciones del protocolo y el
servidor simulado pasó a rechazar estos valores inválidos con `-32600`. Las pruebas
automatizadas verifican ahora los parámetros exactos enviados a `thread/start`.

- [x] Auth, cuota, transporte, timeout, ejecución y cancelación diferenciados.

- [x] Integración real opt-in disponible.
- [x] Ejecución end-to-end live de M02 validada.

M02 queda completado tras superar la integración live con un `CODEX_HOME` de pruebas.

## Limitaciones

- un único worker y una tarea a la vez;
- sin lease distribuido, scheduler, reintentos automáticos ni rotación de cuentas;
- la reconciliación pagina solo la primera página reciente (50 turnos);
- concurrencia live entre ejecuciones y cancelación live quedan pendientes de validar;
- App Server sigue marcado experimental en 0.163.0;
- un thread `LOST` requiere intervención o reconstrucción futura desde documentación;
- no existen approvals interactivos: los threads usan `approvalPolicy="never"`.
