# M03.2 — Conversación persistente de bootstrap

Estado: **COMPLETADO; FLUJO LIVE VALIDADO**  
Fecha: 29 de octubre de 2026

## Alcance

M03.2 crea un único Issue de bootstrap por proyecto, registra o reutiliza el agente
principal y procesa comentarios humanos autorizados mediante tareas e intentos M02.
Publica la respuesta en el mismo Issue y conserva la sesión Codex entre comentarios y
reinicios. No crea archivos, ramas, commits o Pull Requests.

## Arquitectura

```text
CLI -> BootstrapService -> GitHubRegistryService -> GitHub REST
              |
              +-> OrchestratorCore / SQLite
              +-> LocalWorker -> CodexAppServerExecutor
```

No existe un segundo ejecutor: `BootstrapService` crea `Task(BOOTSTRAP_COMMENT)` y
llama a `LocalWorker.run_task()`. Thread, turn, intento, resultado y recuperación usan
el modelo de M02.

La migración `0004_bootstrap_conversation.sql` añade `bootstrap_workflows` y
`bootstrap_comments`. El workflow vincula proyecto, repositorio, Issue y agente. Cada
comentario vincula ID remoto, autor, tarea, respuesta persistida y comentario publicado.

## Agente y prompt

Si falta un principal, se crea idempotentemente como `main`. Su sesión se obtiene con
`get_or_create_session`, de modo que cada intervención reanuda el mismo thread.

Cada turno recuerda que el agente debe explorar objetivos, requisitos, restricciones
y arquitectura; separar propuestas de decisiones aprobadas; no asumir acuerdos; y no
generar código ni pedir operaciones Git.

## Polling y protocolo

El polling explícito lista todos los comentarios paginados, ordena por
`(created_at, id)` y deduplica por `github_comment_id`. El ID, no el timestamp, es la
identidad. Solo se procesa una intervención por ronda.

Los comentarios ordinarios y `/agent main` se dirigen al principal. Los actores tipo
`Bot` se ignoran. Con un token personal, la persona y vibecoder pueden compartir el
mismo login: una respuesta se atribuye a vibecoder por el ID remoto de su operación
`CREATE_COMMENT` completada y persistida, no por coincidir con el login del token.
Actores fuera de la lista local y directivas desconocidas se registran como
`REJECTED` y no crean tareas.

La reclamación `QUEUED → RUNNING` ocurre dentro de una transacción SQLite. Otro
proceso observa `BUSY`. No hay daemon ni polling periódico en este hito.

## Persistencia y recuperación

Estados principales del comentario:

```text
RECEIVED -> QUEUED -> RUNNING -> RESPONSE_PENDING -> COMPLETED
                   \-> BLOCKED
IGNORED / REJECTED
```

Codex termina antes de publicar. Su texto se copia desde el intento exitoso a
`response_text`. Si GitHub falla, queda `RESPONSE_PENDING`; `retry` usa la misma clave
de operación M03.1 y no vuelve a ejecutar Codex.

`recover` examina reclamaciones `RUNNING`. Una tarea que no llegó a intentarse vuelve
a `QUEUED`; una ejecución incierta pasa a `BLOCKED` y conserva el intento `UNKNOWN`.
La reconciliación del turno se realiza con las herramientas de M02 antes de decidir
cualquier repetición.

## Autorización y aprobación

Los usuarios autorizados se suministran con `--authorized-user`; GitHub no puede
modificar esa lista. Una frase de aprobación no cambia estados.

La etiqueta `status:approved` solo es efectiva cuando:

1. está actualmente asignada al Issue;
2. el evento más reciente para esa etiqueta es `labeled`;
3. su actor es humano y está en la lista autorizada;
4. no quedan comentarios recibidos, ejecutándose, pendientes de publicación o
   bloqueados;
5. para workflows nuevos desde M03.3.1, existe una configuración Git estructurada
   confirmada por un usuario autorizado.

Sin atribución verificable el workflow queda `APPROVAL_PENDING`. Al aprobar se guarda
una instantánea Markdown de conversación y respuestas —más la configuración Git en
workflows nuevos—, se impiden nuevas ejecuciones para ese alcance y el proyecto pasa a
`DESIGNING`. Las aprobaciones históricas de M03.2 permanecen válidas, pero no autorizan
efectos remotos nuevos sin reconciliación explícita. No se ejecuta ninguna operación Git.

## CLI

Todas las operaciones reciben base de datos, token externo y usuarios autorizados:

```bash
export VIBECODER_GITHUB_TOKEN='token-externo'

python3 -m vibecoder.bootstrap \
  --database ./vibecoder.sqlite3 \
  --authorized-user alice \
  start PROJECT_ID --description 'Contexto inicial opcional'

python3 -m vibecoder.bootstrap \
  --database ./vibecoder.sqlite3 \
  --accounts ./accounts.json \
  --authorized-user alice \
  poll PROJECT_ID
```

Una invocación `poll` procesa como máximo un comentario. Los demás comandos son:

```bash
python3 -m vibecoder.bootstrap ... status PROJECT_ID
python3 -m vibecoder.bootstrap ... retry PROJECT_ID
python3 -m vibecoder.bootstrap ... recover PROJECT_ID
python3 -m vibecoder.bootstrap ... errors PROJECT_ID
```

El token y los runtimes Codex no se guardan en SQLite.

### Inicialización local para la prueba live

`vibecoder.live_setup` compone exclusivamente el núcleo M01, la configuración runtime
M02 y `GitHubRegistryService` de M03.1. Crea o reutiliza cuenta y proyecto, registra el
repositorio mediante lecturas GitHub y genera `accounts.json` solo cuando no existe.
No crea Issues, comentarios, etiquetas, ramas ni Pull Requests.

```bash
mkdir -p "$HOME/.local/state/vibecoder" "$HOME/.config/vibecoder"
export VIBECODER_GITHUB_TOKEN='token-externo'

.venv/bin/python -m vibecoder.live_setup \
  --database "$HOME/.local/state/vibecoder/m032.sqlite3" \
  --account-name codex-live \
  --project-name vibecoder-test \
  --repository ptobiasdiaz/vibecoder_test \
  --codex-home /ruta/absoluta/al/CODEX_HOME/autenticado \
  --codex-executable /ruta/absoluta/a/codex \
  --working-directory /home/tobias/dev/vibecoder \
  --accounts-json "$HOME/.config/vibecoder/m032-accounts.json"
```

La salida contiene `account_id` y `project_id`, nunca el token. Repetir exactamente el
mismo comando reutiliza los registros. Un `accounts.json` existente e incompatible se
rechaza y no se sobrescribe.

## Pruebas

Suite predeterminada sin red ni inferencia:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -v
```

La integración live está dividida en etapas y exige escritura explícita. Parte de una
base persistente que ya contiene proyecto, cuenta y repositorio M03.1:

```bash
M032_LIVE_WRITE=I_UNDERSTAND_THIS_WRITES_TO_GITHUB \
M032_LIVE_STAGE=start \
M032_GITHUB_TOKEN='token-externo' \
M032_DATABASE=/ruta/m032.sqlite3 \
M032_PROJECT_ID=UUID \
M032_AUTHORIZED_USERS=alice \
.venv/bin/python -m unittest tests.test_bootstrap_live.BootstrapLiveTests -v
```

Después un usuario autorizado comenta manualmente en el Issue. Para ejecutar Codex y
publicar la respuesta:

```bash
M032_LIVE_WRITE=I_UNDERSTAND_THIS_WRITES_TO_GITHUB \
M032_LIVE_STAGE=process \
M032_GITHUB_TOKEN='token-externo' \
M032_DATABASE=/ruta/m032.sqlite3 \
M032_PROJECT_ID=UUID \
M032_AUTHORIZED_USERS=alice \
M032_ACCOUNTS=/ruta/accounts.json \
.venv/bin/python -m unittest tests.test_bootstrap_live.BootstrapLiveTests -v
```

Repetir la etapa `process` tras reiniciar y añadir otro comentario valida continuidad
de sesión. Estas pruebas no se ejecutan automáticamente.

### Resultado live observado

El 29 de octubre de 2026 se validó contra `ptobiasdiaz/vibecoder_test` el flujo
crítico completo:

1. creación idempotente del Issue de bootstrap;
2. lectura de una intervención humana autorizada mediante `/agent main`;
3. creación y ejecución persistente de la tarea Codex mediante M02;
4. persistencia del resultado;
5. publicación de la respuesta en el mismo Issue.

La prueba reveló que un token personal publica con la misma identidad que la persona.
La clasificación inicial ignoraba incorrectamente todas las intervenciones con el
login del token. Se corrigió para atribuir las respuestas propias por el ID remoto de
una operación `CREATE_COMMENT` persistida. El flujo live pasó después de la
corrección. No se repitió todavía una segunda intervención live tras reiniciar el
proceso.

## Criterios de aceptación

- [x] Issue y agente principal idempotentes.
- [x] Polling ordenado, deduplicado y autorizado.
- [x] Tareas, intentos y sesión persistente reutilizan M02.
- [x] Respuesta persistida antes de publicar.
- [x] Reintento de publicación sin repetir Codex.
- [x] Recuperación conservadora y exclusión por Issue.
- [x] Aprobación atribuible y congelación de alcance.
- [x] Pruebas predeterminadas sin GitHub ni inferencia.
- [x] Integración live preparada y desactivada.
- [x] Integración live M03.2 validada para el flujo crítico completo.

## Limitaciones

- polling manual, sin daemon, webhooks ni ETags;
- una intervención por ronda y un worker local;
- usuarios autorizados configurados manualmente;
- sin edición o borrado de comentarios;
- tareas `BLOCKED` requieren reconciliación/decisión operativa;
- snapshot aprobado conserva la conversación, no genera todavía documentos del repo;
- no hay especialistas, preguntas `/reply`, ramas ni Pull Requests;
- continuidad live con una segunda intervención después de reiniciar pendiente de
  observación; la reutilización de sesión tras reinicio sí está cubierta por dobles.
