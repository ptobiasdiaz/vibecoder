# M04.2 — Conversación, planificación y delegación mediante Issues

Estado: **COMPLETADO; FLUJO LIVE VALIDADO**  
Fecha: 31 de octubre de 2026

## Alcance y arquitectura

M04.2 descubre Issues de proyectos activos, mantiene conversaciones persistentes con
el principal y consultas de especialistas, valida planes estructurados, verifica su
aprobación y materializa tareas sin ejecutarlas.

```text
GitHub Issue -> IssueWorkflow -> comentarios -> sesión Issue/agente
             -> PlanRevision -> aprobación atribuida -> PLANNED_WORK (PENDING)
```

Reutiliza `GitHubRegistryService`, operaciones GitHub idempotentes, `LocalWorker`,
sesiones M02, tareas M01 e instrucciones M04.1. No existe un segundo motor de
conversación o ejecución.

## Descubrimiento y autorización

`discover` usa IDs GitHub estables y estado `all`; excluye Pull Requests y el Issue de
bootstrap. Actualiza cierres, reaperturas y etiquetas sin duplicar workflows. Solo
proyectos `ACTIVE` participan.

La allowlist separa identidad del autor, conversador, aprobador y bot. Los comentarios
propios se identifican por IDs de `github_operations`, no por login. Entradas no
autorizadas se registran como rechazadas y nunca provocan Codex ni cambian el plan.

## Enrutamiento y sesiones

Comentarios normales y `/agent main` van al principal. `/agent <especialista>` permite
consultas solo si está `ACTIVE`, su cuenta está disponible y la revisión integrada
coincide con el workspace. Cada Issue/agente tiene una sesión distinta, ligada a
cuenta, workspace y hashes de instrucciones.

`ISSUE_COORDINATION` e `ISSUE_CONSULTATION` pueden ejecutar análisis mediante M02.
`PLANNED_WORK` permanece bloqueado en selección y ejecución dirigida.

## Plan estructurado

El esquema versión 1 exige objetivo, alcance, exclusiones, criterios, riesgos,
suposiciones y tareas. Cada tarea declara ID, descripción, resultado, agente,
dependencias, criterios y restricciones. Se rechazan campos inesperados, vacíos, IDs
inválidos, duplicados, referencias inexistentes, dependencias propias y ciclos.

El JSON canónico es la fuente de verdad y produce SHA-256 reproducible. Markdown se
publica con revisión y hash. Una respuesta del principal puede contener exactamente un
bloque fenced `vibecoder-plan`; uno inválido nunca se convierte en plan.

Estados: `DRAFT`, `PROPOSED`, `CONFIRMED`, `APPROVED`, `SUPERSEDED` y `BLOCKED`. Una
modificación crea otra revisión y no sobrescribe las aprobadas.

## Aprobación repetida y congelación

Una revisión `CONFIRMED` solo pasa a `APPROVED` con `status:approved` presente y un
evento `labeled` de usuario autorizado, posterior al comentario exacto y no usado por
otra aprobación. Mantener la etiqueta no aprueba una revisión nueva: debe retirarse y
reaplicarse.

La congelación conserva Issue, conversación completada, plan, asignaciones,
dependencias, aprobador y snapshot de agentes, cuentas, revisiones e instrucciones.

## Materialización y recuperación

La materialización idempotente crea una tarea `PLANNED_WORK` por ID lógico y conserva
`planned_task_dependencies`. Antes compara el snapshot actual. Una deriva bloquea el
workflow sin alterar la aprobación histórica.

Las respuestas se persisten antes de publicar. Un fallo GitHub reintenta solo la
publicación. Un turno incierto queda bloqueado para reconciliación M02. Reiniciar
recupera workflows, cursores, sesiones, planes, aprobaciones y tareas sin reenvíos.

## Persistencia

`0009_issue_coordination.sql` añade `issue_workflows`, `issue_comments`,
`issue_agent_sessions`, `plan_revisions`, `planned_tasks`, dependencias y
`plan_approval_events`.

## CLI

```bash
python -m vibecoder.issues --database STATE.sqlite3 --workspace PROJECT \
  --authorized-user USER discover PROJECT_ID
python -m vibecoder.issues ... list PROJECT_ID
python -m vibecoder.issues ... poll WORKFLOW_ID
python -m vibecoder.issues ... --accounts accounts.json process WORKFLOW_ID
python -m vibecoder.issues ... plan WORKFLOW_ID --file plan.json --agent-id MAIN_AGENT_ID
python -m vibecoder.issues ... plans WORKFLOW_ID
python -m vibecoder.issues ... propose-plan PLAN_REVISION_ID
python -m vibecoder.issues ... approve-check PLAN_REVISION_ID
python -m vibecoder.issues ... materialize PLAN_REVISION_ID
python -m vibecoder.issues ... tasks PLAN_REVISION_ID
python -m vibecoder.issues ... reconcile WORKFLOW_ID
```

Los comandos locales no necesitan token. Los que acceden a GitHub exigen el token
externo. `process` también exige `accounts.json` y consume cuota Codex.

```bash
.venv/bin/python -m unittest discover -s tests -q
```

Las pruebas live opt-in están separadas por `discover`, `process`, `publish-plan`,
`approve`, `materialize` y `recover` en `tests/test_issues_live.py`. Variables:

```text
M042_LIVE_WRITE=I_UNDERSTAND_THIS_WRITES_TO_GITHUB
M042_LIVE_STAGE=<etapa>
M042_DATABASE, M042_PROJECT_ID, M042_ISSUE_NUMBER
M042_WORKSPACE, M042_AUTHORIZED_USER, VIBECODER_GITHUB_TOKEN
M042_ACCOUNTS                 # solo process

M042_PLAN_REVISION_ID         # approve/materialize
```

`process` escribe comentario y consume cuota. `publish-plan` escribe comentario.
`discover` puede crear la etiqueta. `materialize` solo escribe SQLite. No hay ramas,
commits o PR de implementación.

### Resultado live observado

El 31 de octubre de 2026 se continuó desde el proyecto de pruebas activo de M04.1.
El flujo real descubrió un Issue, procesó intervenciones autorizadas del desarrollador,
publicó respuestas del agente principal y del especialista `testing`, y mantuvo
sesiones aisladas por Issue/agente. Se publicaron dos revisiones estructuradas del
plan. La etiqueta perteneciente a la primera revisión no autorizó la segunda; solo un
nuevo evento atribuible tras retirar y reaplicar `status:approved` permitió aprobarla.

La revisión final quedó congelada y sus tareas se materializaron idempotentemente en
estado `PENDING`, con dependencias persistidas y sin intentos de ejecución. Tras
reiniciar el proceso, el workflow se recuperó en `MATERIALIZED`. No se crearon ramas,
commits ni Pull Requests de implementación.

## Limitaciones

- polling manual y sin locks distribuidos;
- sin ejecución de `PLANNED_WORK`, workspaces de implementación ni PR;
- sin matching semántico automático de especialistas;
- sin negociación GitHub de especialistas nuevos;
- sin ejecución de las tareas materializadas, deliberadamente reservada para M04.3.

## Criterios de aceptación

- [x] Descubrimiento idempotente, cierres/reaperturas y exclusiones.
- [x] Conversación principal y consultas con sesiones aisladas.
- [x] Planes tipados, revisiones, hashes y dependencias acíclicas.
- [x] Aprobación por evento nuevo atribuible y congelación completa.
- [x] Materialización idempotente y ejecución bloqueada.
- [x] Recuperación conservadora y pruebas offline.
- [x] Pruebas live opt-in preparadas.
- [x] Flujo live completo ejecutado y recuperado tras reinicio.
