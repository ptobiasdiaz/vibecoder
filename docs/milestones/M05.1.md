# M05.1 — Empaquetado Debian/Ubuntu y systemd

## Estado

**IMPLEMENTADO; BUILD E INSTALACIÓN AISLADA VALIDADOS EN DEBIAN FORKY. EJECUCIÓN
BAJO SYSTEMD REAL PENDIENTE.**

## Alcance

M05.1 distribuye el runtime como paquete Debian estándar, sin checkout ni virtualenv,
crea una identidad sin login, prepara rutas FHS e instala un supervisor systemd que
arranca en espera segura. No incorpora administración completa, debconf, panel web ni
instalación de Codex.

## Arquitectura y dependencias

El paquete nativo usa `debhelper-compat 13`, `dh-python`, pybuild y setuptools.
`dh_installsystemd` instala y habilita la unidad. Los entrypoints proceden de
`pyproject.toml`; `vibecoder-supervisor` reutiliza M04.5.

Runtime obligatorio: Python 3.11+, `python3-httpx >= 0.27`, `python3-pydantic >= 2.7`,
Git, certificados CA, `adduser` y systemd. Codex es una dependencia operativa configurable,
no un paquete APT ni requisito de instalación.

## Primer arranque

La configuración instalada no contiene secretos/proyectos y usa
`operational_state: NOT_CONFIGURED`, con lecturas, inferencia y publicaciones
deshabilitadas. `run` permanece activo y responde a SIGTERM; `once` devuelve
`inactive: 1` sin programar trabajo. Configuraciones anteriores sin el campo conservan
`READY` por compatibilidad con M04.

M05.2/M05.3 validarán recursos y realizarán la transición administrativa a `READY`.

## Ciclo Debian, permisos y seguridad

`postinst` crea `vibecoder:vibecoder`, sin login, y ajusta solo directorios propios.
No ejecuta Git, Codex, pip ni red. Las configuraciones son conffiles y los datos no se
sustituyen en upgrades. `postrm` preserva datos e identidad incluso en purge.

La unidad aplica hardening compatible con Git/Codex y deja writable solo estado,
runtime y temporales privados. El token se recibe opcionalmente desde un archivo de
entorno externo; no se instala ninguno. El servicio nunca corre como root.

## Construcción y pruebas

```bash
dpkg-buildpackage -us -uc -b
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
systemd-analyze verify debian/vibecoder.service
```

Las pruebas inspeccionan metadatos, dependencias, configuración inerte, entrypoint,
migraciones, unidad, scripts, permisos y exclusión de estado de desarrollo. El `.deb`
se inspecciona mediante `dpkg-deb`; no se instala en el host de desarrollo.

Resultados observados el 2026-10-31:

- build Debian forky: 264 tests correctos, 45 live opt-in omitidos antes de la mejora
  final del loop inactivo;
- suite final del host: 265 tests correctos, 45 omitidos;
- dos builds `nocheck` byte a byte idénticos; el checksum se publica junto al
  artefacto y no dentro del propio paquete para evitar una referencia circular;
- instalación en contenedor forky: usuario, grupo, permisos, entrypoint, migraciones y
  estado `NOT_CONFIGURED` correctos;
- reinstalación, remove y purge conservaron SQLite y la identidad;
- unidad habilitada y aceptada por `systemd-analyze verify`.
- `lintian --display-info --pedantic` sin hallazgos del paquete.
- `run` en `NOT_CONFIGURED` permaneció inerte, no generó actividad periódica en
  SQLite y aceptó SIGTERM.

## Compatibilidad y limitaciones

- Build e instalación validados en contenedor Debian forky; no se instaló en el host.
- Ubuntu queda sin declarar validado hasta probar una versión concreta.
- La conducta real de la unidad requiere VM o contenedor con systemd.
- Sin debconf, administración completa, backups ni repositorio APT.
- La política exhaustiva de backup/migración queda para M05.4.

Los archivos, build reproducible, instalación, reinstalación, remove y purge cumplen el
alcance comprobable en contenedor. No se declara validación del proceso de larga
duración bajo systemd hasta probarlo en una VM o contenedor con systemd como PID 1.
