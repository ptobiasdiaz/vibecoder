# M06.13 — Recuperación, cuotas y bases Git

M06.13 corrige tres defectos observados durante el uso real: reutilización de
claves terminales al reintentar planes, tratamiento terminal de la cuota y uso
indefinido del SHA registrado inicialmente.

Se incorporan intentos inmutables, clasificación de fallos, backoff persistente,
reintentos administrativos y consulta del HEAD remoto para tareas
independientes, conservando la herencia del DAG. `UNKNOWN`, las aprobaciones de
planes y el merge humano mantienen su semántica.

## Validación live en Debian Sid

Se reinstaló mediante APT el candidato corregido 0.0.1 en la VM autorizada.
La identidad GitHub, el worker Codex autenticado, los proyectos, las sesiones y
el historial se conservaron. El daemon y el launcher quedaron activos, GitHub
`ONLINE`, el worker `READY`, SQLite íntegra y sin barreras de recuperación.

La recuperación se hizo exclusivamente mediante la API administrativa:

```bash
vibecoder plan retry ptobiasdiaz/vibecoded_breakout 16
vibecoder task retry 1bb9cf67-401e-50bf-ad34-36ec600ff7bd
vibecoder task retry b5da779e-9d56-5794-93df-f688e071ae63
```

No se modificó SQLite para alterar estados.

### Issue #14

La tarea raíz partió del HEAD remoto verificado
`99d5d9b225ab5592260e11273ce1a5ee0848e8bc`, en lugar del SHA de registro
obsoleto. Produjo `a60cf8ff792171ed29e3c70830f8cc655c58dcac`. La tarea
dependiente registró ese mismo SHA como base `DEPENDENCY` y produjo
`710423e431a6700e289e5b45235a433b5bf54de8`. Se publicaron, una sola vez,
los PR #17 y #19.

### Issue #15

La tarea raíz también partió de `99d5d9b225ab5592260e11273ce1a5ee0848e8bc`.
Las cuatro tareas terminaron correctamente y sus descendientes registraron
bases de tipo `DEPENDENCY`. Se publicaron los PR #18, #20, #21 y #22 sin
duplicados.

### Issue #16

El reintento de plan creó el intento inmutable
`823900a0-708a-4e76-8b1c-5930355a7ebb` y la revisión con hash
`e2bc071475f70b51986a9bcef657119d1100ec393ad41c3ee092384ddaafb9b7`, sin
reutilizar las ejecuciones terminales antiguas. La aprobación se recibió como
comentario humano autorizado de GitHub y coincidía exactamente con ese hash.

Las tareas t1–t5 terminaron mediante Codex real y publicaron los PR #23–#27.
t6 dependía de cuatro resultados paralelos. Su integración local encontró un
conflicto antes de iniciar Codex o producir efectos remotos. El intento quedó
`FAILED/FUNCTIONAL` y la tarea `BLOCKED`, sin barrera `UNKNOWN`. La continuación
segura requiere integrar humanamente los PR abiertos y solicitar una nueva
revisión que parta de esa base integrada; vibecoder no fusiona resultados
paralelos conflictivos ni reutiliza la aprobación anterior.

Tras completar #14 y #15 se reinició el daemon. Los estados terminales y los
PR permanecieron estables y el polling posterior no produjo duplicados.
