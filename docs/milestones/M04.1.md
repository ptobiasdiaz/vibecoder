# M04.1 — Gestión de agentes especializados

Estado: **COMPLETADO; VALIDACIÓN LIVE LOCAL SUPERADA**  
Fecha: 30 de octubre de 2026

## Alcance

M04.1 añade definición, revisión, activación, suspensión, reactivación y retirada de
especialistas en proyectos `ACTIVE`. Reutiliza `Agent`, cuentas y sesiones existentes.
La creación, asignación y ejecución de tareas especializadas permanece bloqueada hasta
el hito de enrutamiento; no asigna Issues ni publica cambios GitHub.

## Modelo y persistencia

La identidad estable sigue en `agents`. La migración
`0008_specialized_agents.sql` añade:

- `specialist_agents`: ID lógico por proyecto, estado, cuenta y revisión activa;
- `agent_configuration_revisions`: contenido estructurado, versión, hashes, commit y
  autorización;
- `agent_audit_events`: actor, operación, estados/versiones anterior y nueva,
  resultado y fecha.

Los estados son `DRAFT → PROPOSED → ACTIVE ↔ SUSPENDED → RETIRED`. Una retirada es
final y no libera el identificador. Las revisiones avanzan de `PROPOSED` a
`VALIDATED` y `ACTIVE`; una nueva activa marca la anterior `SUPERSEDED`.

## Instrucciones y Git

Cada especialista usa `.vibecoder/agents/<agent-id>/AGENTS.md`. La precedencia es:
seguridad del orquestador, `AGENTS.md` raíz, instrucciones específicas, memoria y
tarea. El cargador registra SHA-256 del archivo global sin duplicar su texto y carga
explícitamente el específico.

La validación comprueba ruta, symlinks, hash y conflictos explícitos `Rule:`. La
activación además exige checkout limpio, rama principal aprobada y el mismo contenido
en `HEAD`. Una edición local, aunque esté validada, no es configuración activa. M04.1
no crea el PR necesario para integrarla.

## Cuentas y sesiones

Cada especialista referencia una cuenta real existente. No se almacenan secretos. La
cuenta solo puede cambiar con autorización y con el agente no activo. Los threads
históricos permanecen asociados a su cuenta original; al reactivar con otra cuenta se
crea o recupera únicamente una sesión compatible. Identidad lógica y sesión siguen
siendo entidades distintas.

## Autorización, recuperación y consistencia

Las mutaciones administrativas requieren `--actor` y, para estados o cuenta,
`--authorize`. También se auditan rechazos por falta de autorización. Tras reiniciar,
SQLite recupera estados y revisiones. `check` diagnostica proyecto, cuenta, deriva de
instrucciones y sesiones históricas incompatibles. No activa, reejecuta ni descarta
nada automáticamente.

La suspensión o retirada se rechaza si hay una tarea `RUNNING`. Un agente no activo
no admite tareas nuevas ni sesiones. La detección semántica completa de conflictos en
lenguaje natural no se promete: los casos no deterministas requieren revisión.

## CLI

```bash
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER list PROJECT_ID
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER propose PROJECT_ID backend \
  --name Backend --role "Backend engineering" \
  --responsibility "Implementar cambios backend aprobados" \
  --capability "Modificar backend y pruebas" \
  --restriction "No ampliar el alcance" \
  --instructions-file backend-AGENTS.md --account ACCOUNT_ID
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER validate AGENT_ID
```

Después de revisar e integrar el archivo en la rama principal local:

```bash
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER activate AGENT_ID --authorize
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER check AGENT_ID
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER history AGENT_ID
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER suspend AGENT_ID --authorize
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER resume AGENT_ID --authorize
python -m vibecoder.agents --database STATE.sqlite3 --workspace PROJECT --actor USER retire AGENT_ID --authorize
```

### Resultado live observado

El 30 de octubre de 2026 se continuó desde el proyecto de pruebas activado por M03.4.
Se propuso y validó un especialista, se integraron localmente sus instrucciones
versionadas, se activó con una cuenta Codex real ya configurada y se creó su referencia
de sesión sin ejecutar inferencia. La reapertura de SQLite recuperó identidad,
configuración, cuenta y sesión. También se verificaron suspensión y reactivación sin
perder historial ni cambiar de identidad. No se realizó push, PR ni escritura GitHub.

## Limitaciones

- negociación y aprobación GitHub, PR de instrucciones y asignación de Issues quedan
  para hitos posteriores;
- no hay creación, asignación ni ejecución de tareas de especialistas ni scheduler;
- no se interrumpe una tarea en curso para suspender o retirar;
- los conflictos semánticos no estructurados requieren revisión humana;
- la prueba live no ejecutó un turno Codex, de acuerdo con el alcance de M04.1; la
  ejecución de tareas especializadas permanece reservada para un hito posterior.

## Criterios de aceptación

- [x] Identidad persistente y única por proyecto.
- [x] Configuración versionada, hash reproducible y auditoría.
- [x] Propuesta, validación, activación, suspensión, reactivación y retirada.
- [x] Jerarquía `AGENTS.md`, rutas seguras y bloqueo por deriva/conflicto.
- [x] Cuenta por agente y sesiones compatibles independientes de la identidad.
- [x] Recuperación conservadora y compatibilidad con agentes `main` históricos.
- [x] Pruebas offline y prueba live opt-in preparadas.
- [x] Validación live local de persistencia y ciclo de vida ejecutada.
