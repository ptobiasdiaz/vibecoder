# M01 — Núcleo persistente del orquestador

Estado: **COMPLETADO**  
Fecha: 28 de octubre de 2026

## Alcance

M01 implementa una biblioteca Python persistente e independiente de transportes para
administrar cuentas Codex, proyectos, agentes lógicos, sesiones, tareas e intentos de
ejecución. No contiene FastAPI, GitHub, Telegram, Docker, inferencia ni un gestor de
autenticación.

El alcance sustituye la descripción antigua del roadmap que agrupaba API, Docker,
webhooks y colas en M01. Esas integraciones quedan fuera de este núcleo y se abordarán
en los hitos que correspondan.

## Componentes

- `vibecoder.domain`: entidades inmutables, enumeraciones y máquinas de estados.
- `vibecoder.service.OrchestratorCore`: fachada de casos de uso y transacciones
  compuestas.
- `vibecoder.ports.Repository`: contrato entre aplicación y almacenamiento.
- `vibecoder.ports.CodexExecutor`: contrato mínimo para el futuro adaptador Codex.
- `vibecoder.sqlite.SQLiteRepository`: implementación SQLite de M01.
- `vibecoder/migrations`: migraciones SQL versionadas.

El prototipo `m00_codex` permanece separado. M01 reutiliza sus conclusiones sobre el
ciclo de vida de threads, pero no convierte el cliente experimental en producción ni
ejecuta inferencia.

## Modelo de dominio

| Entidad | Responsabilidad |
|---|---|
| `CodexAccount` | Modo de autenticación, referencia no secreta al entorno y disponibilidad. |
| `Project` | Proyecto lógico, repositorio GitHub opcional y cuenta asignada. |
| `Agent` | Identidad lógica principal o especializada dentro de un proyecto. |
| `AgentSession` | Asociación agente–cuenta–thread y estado de persistencia Codex. |
| `Task` | Unidad de trabajo asignada a un agente, con clave de idempotencia opcional. |
| `ExecutionAttempt` | Intento numerado, resultado y error estructurado de una tarea. |

`credential_ref` es una referencia como `codex-home://account-main` o una clave de un
secret store; nunca contiene el token o API key. Una cuenta puede servir a varios
agentes. Una sesión no puede cambiar implícitamente de cuenta.

## Esquema y persistencia

La migración `0001_initial.sql` crea:

- `schema_migrations` para registrar versiones aplicadas;
- `codex_accounts`, `projects`, `agents`, `agent_sessions`, `tasks` y
  `execution_attempts`;
- claves primarias UUID en texto y claves foráneas con `foreign_keys=ON`;
- unicidad de nombres, repositorios, thread IDs, referencias externas y claves de
  idempotencia dentro de cada proyecto;
- un único agente principal por proyecto;
- triggers que impiden asociar tareas con agentes de otro proyecto y sesiones con una
  cuenta distinta de la del proyecto.

Las operaciones compuestas usan `BEGIN IMMEDIATE`, commit o rollback. El servicio
depende del puerto `Repository`; las decisiones de dominio no importan `sqlite3`, lo
que prepara una implementación PostgreSQL posterior sin incluirla en M01.

## Estados y transiciones

### Tareas

```text
PENDING -> RUNNING | CANCELLED
RUNNING -> WAITING | WAITING_QUOTA | WAITING_AUTH | COMPLETED | FAILED | CANCELLED
WAITING -> RUNNING | FAILED | CANCELLED
WAITING_QUOTA/WAITING_AUTH -> RUNNING | WAITING | FAILED | CANCELLED
FAILED -> PENDING
COMPLETED/CANCELLED -> terminal
```

El paso `FAILED -> PENDING` representa una decisión explícita de reintento. Iniciar un
intento mueve la tarea a `RUNNING`; finalizarlo la mueve a `COMPLETED`, `FAILED` o
`WAITING` si el resultado es desconocido.

### Sesiones

```text
NOT_CREATED
  -> THREAD_CREATED_UNCONFIRMED
  -> THREAD_PERSISTED
  -> RECOVERABLE

UNAVAILABLE puede alcanzarse temporalmente desde estados activos.
LOST es terminal para esa sesión técnica.
```

No se permite saltar de `THREAD_CREATED_UNCONFIRMED` a `RECOVERABLE`: M00 demostró que
crear un thread vacío no garantiza persistencia. Solo después de confirmar un turno se
marca `THREAD_PERSISTED`.

## Idempotencia y recuperación

`create_task` acepta `idempotency_key`. Repetir la misma operación devuelve la tarea
existente; reutilizar la clave con datos diferentes genera `ConflictError`. SQLite
refuerza la garantía con un índice único.

Después de reiniciar, `recover_interrupted_tasks()` busca tareas `RUNNING`, marca sus
intentos abiertos como `UNKNOWN` con código `PROCESS_RESTARTED` y mueve las tareas a
`WAITING`. No reejecuta nada: un operador o reconciliador futuro debe determinar si el
efecto externo ocurrió antes de volver a `RUNNING`.

## Uso

```python
from vibecoder import OrchestratorCore, SQLiteRepository

with SQLiteRepository("vibecoder.sqlite3") as repository:
    core = OrchestratorCore(repository)
    account = core.register_account("main", "CHATGPT", "codex-home://main")
    project = core.register_project("demo", account.id)
    agent = core.register_agent(
        project.id,
        "main",
        "PRINCIPAL",
        config_ref="config/agents.yaml#main",
        documentation_ref="README.md",
    )
    task = core.create_task(
        project.id, agent.id, "BOOTSTRAP", idempotency_key="bootstrap-1"
    )
```

Ejemplo completo que cierra y vuelve a abrir el servicio:

```bash
python3 -m examples.m01_persistence
```

## Pruebas

```bash
python3 -m unittest discover -v
```

La suite de M01 cubre:

- altas y consultas de cuentas, proyectos, agentes y sesiones;
- asignación de cuenta y prohibición de transferencia con sesiones existentes;
- transiciones válidas e inválidas de tareas y sesiones;
- intentos y errores estructurados;
- integridad referencial en servicio y almacenamiento;
- persistencia tras cerrar y reabrir SQLite;
- recuperación conservadora de tareas interrumpidas;
- aislamiento entre proyectos e idempotencia.

Todas las pruebas se ejecutan localmente, sin GitHub, credenciales ni inferencia.

## Criterios de aceptación

- [x] Biblioteca Python con interfaz programática clara.
- [x] Entidades persistentes de M01 y asociaciones íntegras.
- [x] SQLite con migraciones, FKs, restricciones y transacciones.
- [x] Máquinas de estados explícitas para tareas y sesiones.
- [x] Intentos, errores estructurados e idempotencia.
- [x] Recuperación conservadora después de reiniciar.
- [x] Puerto independiente para el futuro ejecutor Codex.
- [x] Pruebas automatizadas sin servicios externos.
- [x] Ejemplo de cierre y recuperación de datos.

## Limitaciones conocidas

- No hay locking distribuido, scheduler ni cola externa.
- El núcleo presupone un único proceso escritor coordinado; SQLite serializa las
  transacciones locales.
- No hay todavía reconciliador con Codex o GitHub para resolver intentos `UNKNOWN`.
- El puerto `CodexExecutor` es intencionalmente mínimo y podrá ampliarse al integrar
  el adaptador, manteniéndolo separado de autenticación y persistencia.
- PostgreSQL, API web, Docker, GitHub y observabilidad quedan fuera de M01.
