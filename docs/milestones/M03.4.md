# M03.4 — Publicación remota, Pull Request y activación

Estado: **COMPLETADO; FLUJO REMOTO LIVE VALIDADO**  
Fecha: 30 de octubre de 2026

## Alcance

M03.4 publica exclusivamente una generación M03.3 validada y autorizada por M03.3.1.
Inicializa remotos vacíos, publica la rama bootstrap, crea o recupera un PR, observa el
merge humano y activa el proyecto. No fusiona ni automatiza desarrollo posterior.

## Arquitectura y persistencia

```text
bootstrap APPROVED -> git config APPROVED/APPLIED -> generation READY_TO_PUBLISH
  -> publication -> base -> rama bootstrap -> PR -> merge verificado -> ACTIVE
```

`0007_remote_publication.sql` añade `publication_workflows` y
`publication_operations`. Conservan ramas, SHA, PR, snapshot remoto, bloqueos,
activación e intención previa de cada push. Estados: `READY`, `INITIALIZING_BASE`,
`BASE_READY`, `PUSHING_BRANCH`, `BRANCH_PUBLISHED`, `CREATING_PR`,
`WAITING_FOR_MERGE`, `MERGED`, `ACTIVATED`, `BLOCKED` y `UNKNOWN`.

## Autorización

`prepare` comprueba proyecto, repositorio, bootstrap, configuración, hashes,
operaciones enumeradas, generación, validación, rama, workspace limpio, HEAD,
parentesco con el commit base y permisos GitHub. La autorización se comprueba otra vez
antes de avanzar. Ni texto libre ni Codex pueden ordenar efectos remotos.

## Repositorios vacíos

GitHub no permite crear refs mediante la API Git en repositorios sin ramas. La guía
oficial propone Contents API; M03.4 usa el primer `git push` porque ya dispone del
commit aprobado y evita un canal paralelo ([refs](https://docs.github.com/en/rest/git/refs#create-a-reference),
[Git database](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-your-git-database)).

M03.3 crea para generaciones nuevas un commit raíz vacío, con identidad, fecha fija y
mensaje reproducibles. El código generado se confirma encima. M03.4 publica primero
el SHA técnico como rama principal y verifica referencia y default branch; después
publica solo el SHA generado. Una generación histórica incompatible se conserva pero
requiere regeneración explícita.

## Git, credenciales y seguridad

Git usa argumentos separados, `GIT_TERMINAL_PROMPT=0`, `--no-verify` y nunca force.
HTTPS usa un `GIT_ASKPASS` temporal 0700; el token solo entra en el entorno de Git, se
redacta de errores y no se persiste en URL, argv, configuración, logs, SQLite o
workspace. Codex nunca recibe ese entorno. Esto limita exposición accidental, pero no
sustituye un sandbox fuerte de sistema operativo.

## Recuperación, PR y merge

Antes del push se guarda intención; después se consulta GitHub y se exige el SHA. Un
fallo produce `UNKNOWN`; `reconcile` consulta refs antes de reintentar. Una rama con
SHA distinto bloquea y nunca se sobrescribe.

El PR incluye Issue, generación, hashes, ramas, commit y advertencia de revisión. Se
busca por head/base y marcador antes de crear; un PR ajeno bloquea. Una respuesta
perdida se reconcilia sin duplicar.

El polling consulta el PR. GitHub documenta que `mergeable` puede ser `null` y que
`merge_commit_sha` depende del método de merge; se usan `merged`, SHA final y refs
head/base ([Pull Requests API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)).
Un PR cerrado sin merge bloquea. Tras verificar identidad y rama principal, el
proyecto pasa idempotentemente de `DESIGNING` a `READY` y `ACTIVE`.

## CLI

```bash
python3 -m vibecoder.publication --database STATE.sqlite3 prepare PROJECT_ID
python3 -m vibecoder.publication --database STATE.sqlite3 status PROJECT_ID
python3 -m vibecoder.publication --database STATE.sqlite3 next PUBLICATION_ID
python3 -m vibecoder.publication --database STATE.sqlite3 reconcile PUBLICATION_ID
python3 -m vibecoder.publication --database STATE.sqlite3 pr PUBLICATION_ID
python3 -m vibecoder.publication --database STATE.sqlite3 check-merge PUBLICATION_ID
python3 -m vibecoder.publication --database STATE.sqlite3 activate PUBLICATION_ID
python3 -m vibecoder.publication --database STATE.sqlite3 errors PUBLICATION_ID
```

Cada `next` realiza como máximo un efecto. `pr` solo consulta; nunca crea ni fusiona.

## Pruebas live opt-in

Lectura:

```bash
M034_LIVE_READ=I_UNDERSTAND_THIS_READS_GITHUB \
.venv/bin/python -m unittest \
  tests.test_publication_live.PublicationReadLiveTests.test_remote_status -v
```

Las escrituras exigen
`M034_LIVE_WRITE=I_UNDERSTAND_THIS_PUSHES_AND_CREATES_A_PR` y se ejecutan una a una
con `M034_STAGE=prepare`, `base`, `branch` y `pr`. Dejan ramas y PR abierto. Tras merge
manual se ejecutan `merge` y `activate`. Variables comunes: `M034_DATABASE`,
`M034_PROJECT_ID`, `M034_GITHUB_TOKEN`.

### Resultado live observado

El 30 de octubre de 2026 se validó el flujo completo contra el repositorio de pruebas
`ptobiasdiaz/vibecoder_test`, recreado completamente vacío. GitHub aceptó el primer
push del commit técnico, reconoció la rama principal aprobada como predeterminada y
confirmó su SHA. A continuación se publicó la rama bootstrap con el commit generado,
se creó un único Pull Request trazable y un desarrollador lo revisó y fusionó
manualmente. El polling distinguió el merge del simple cierre, persistió el SHA de
merge y activó el proyecto. La recuperación del estado no generó ramas, commits o PR
duplicados y vibecoder no realizó el merge.

## Limitaciones

- polling manual, un publicador local y sin lock distribuido;
- sin webhooks, merge automático ni borrado de ramas;
- el token existe brevemente en el entorno de Git;
- remotos no HTTPS dependen de su autenticación externa;
- generaciones históricas incompatibles requieren regeneración;
- cualquier deriva futura de identidad, rama o SHA bloquea en lugar de corregirse
  silenciosamente.

## Criterios de aceptación

- [x] Autorización específica, hashes y estado remoto verificados.
- [x] Base técnica y rama alternativa soportadas.
- [x] Push sin force e idempotencia conservadora.
- [x] PR trazable, recuperable y sin duplicados.
- [x] Merge humano verificado y activación idempotente.
- [x] Persistencia, recuperación, pruebas offline y live opt-in preparadas.
- [x] Flujo remoto validado live.
