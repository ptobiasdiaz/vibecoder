# M00 — Validación técnica de Codex

Estado: **COMPLETADO**  
Versión observada: `codex-cli 0.163.0` (28 de octubre de 2026)

## Objetivo y alcance

Este hito valida el adaptador técnico que necesitará el futuro orquestador, sin
implementarlo. El prototipo inicia Codex App Server desde Python, habla su protocolo
JSONL oficial por stdio y ensaya threads, turnos, eventos, errores, límites,
aislamiento, reinicio, concurrencia y cancelación.

No incluye API web, base de datos, colas, contenedores, GitHub ni política de
orquestación. El código vive en `m00_codex/` y sus pruebas en `tests/` para mantenerlo
separado de la implementación futura.

## Arquitectura del prototipo

`AppServerClient` crea un proceso hijo:

```text
Python -> codex app-server --listen stdio://
       <- JSONL por stdout; diagnósticos por stderr
```

La conexión envía `initialize`, espera la respuesta y notifica `initialized`. Cada
petición tiene ID y un `Future`; un lector único correlaciona respuestas y coloca las
notificaciones en una cola. Los métodos experimentados son:

- `thread/start`, `thread/read`, `thread/list` y `thread/resume`;
- `turn/start` y `turn/interrupt`;
- eventos `item/agentMessage/delta` y `turn/completed`;
- `account/rateLimits/read` y `account/usage/read`.

El estado final se toma de `turn/completed`. Solo `completed` es éxito; `failed` e
`interrupted` se conservan como resultados distintos. Los errores RPC se clasifican
de forma conservadora como autenticación, cuota o ejecución, manteniendo siempre el
código y mensaje originales.

## Instalación y ejecución

Requiere Python 3.11 o posterior y una instalación de Codex con `app-server`.
No hay dependencias Python de ejecución externas.

```bash
python3 -m unittest discover -v
python3 -m m00_codex.diagnostic
```

El diagnóstico busca `codex` en `PATH` y, para esta instalación empaquetada, en
`~/.codex/packages/app-server-daemon/releases/*/bin/codex`. Puede indicarse de forma
explícita:

```bash
python3 -m m00_codex.diagnostic --codex /ruta/a/codex --json
```

Por defecto usa un `CODEX_HOME` temporal nuevo y no hace inferencia. Para conservar
el entorno de prueba entre ejecuciones se puede proporcionar una ruta dedicada:

```bash
python3 -m m00_codex.diagnostic --codex-home /ruta/aislada/m00-home
```

Nunca debe pasarse el `~/.codex` habitual a pruebas que creen threads.

### Integración opcional

La integración local sin inferencia es opt-in:

```bash
M00_CODEX_INTEGRATION=1 python3 -m unittest tests.test_integration -v
```

La prueba live exige además un home aislado y autenticado. Puede consumir una
cantidad pequeña de cuota:

```bash
M00_CODEX_INTEGRATION=1 \
M00_CODEX_LIVE=1 \
M00_CODEX_HOME=/ruta/aislada/y/autenticada \
M00_CODEX_BIN=/ruta/a/codex \
python3 -m unittest tests.test_integration -v
```

## Autenticación

La autenticación pertenece a cada `CODEX_HOME`. Debe prepararse fuera del repositorio
con el flujo soportado por la instalación de Codex. No se guardan ni se imprimen
tokens. Para una cuenta con OAuth gestionado externamente, la documentación oficial
también admite arrancar App Server con un proveedor Responses y pasar el token al
proceso hijo mediante una variable de entorno; la renovación requiere reiniciar el
proceso y reanudar el thread.

La prueba inicial basada en una copia temporal de `auth.json` falló con
`workspace routing discovery failed`, por lo que copiar un archivo de credenciales no
se considera un procedimiento universal de aprovisionamiento. Posteriormente se
preparó un `CODEX_HOME` de prueba correctamente autenticado y la prueba crítica de
persistencia terminó satisfactoriamente. No se modificaron sesiones del usuario.

Las decisiones de autenticación posteriores a M00 se registran en
[ADR-0002](../decisions/ADR-0002-authentication.md). M00 no implementa todavía el
gestor de autenticación.

## Pruebas y resultados observados

| Capacidad | Tipo | Resultado en 0.163.0 |
|---|---|---|
| Arranque y handshake | Real, home temporal | Confirmada |
| Protocolo oficial JSONL/stdio | Real y simulada | Confirmado |
| Crear threads independientes | Real y simulada | Confirmado |
| Reanudar dentro de una conexión | Simulada | Confirmado en cliente |
| Reiniciar y reanudar antes del primer turno | Real | No disponible: `no rollout found` |
| Persistencia después de un turno completado | Live | Confirmada tras reiniciar App Server |
| Dos threads concurrentes | Simulada | Confirmado; live pendiente para evitar consumo |
| Consultar límites/uso | Método y esquema real | Disponible; datos requieren autenticación compatible |
| Errores de auth/cuota/ejecución | Simulada + fallo live | Clasificación confirmada; catálogo exhaustivo pendiente |
| Dos `CODEX_HOME` aislados | Proceso y unitarias | Confirmado a nivel de entorno/almacenamiento; multicuenta live pendiente |
| Cancelación y estado `interrupted` | Simulada + protocolo oficial | Confirmado en cliente; live pendiente |

Resultados automatizados de esta entrega: seis pruebas unitarias pasan; las pruebas
reales están desactivadas por defecto. La ejecución live aportada para el cierre fue:

```text
test_empty_thread_is_not_persisted_before_first_turn ... ok
test_persist_after_turn_and_resume_after_restart ... ok

Ran 2 tests in 5.114s

OK
```

Queda observado que un ID creado por `thread/start` no es durable hasta que existe un
rollout asociado a un turno. Tras completar un turno real, el thread sí puede
reanudarse después de reiniciar App Server.

La documentación oficial de App Server confirma que `thread/resume` reabre un thread
almacenado, `turn/interrupt` debe finalizarlo como `interrupted` y
`account/rateLimits/read` expone ventanas de cuota de ChatGPT. Esas afirmaciones se
marcan aquí separadamente de los resultados observados en esta cuenta.

## Limitaciones y alternativas

- La disponibilidad del método no implica que la cuenta pueda usarlo. El diagnóstico
  informa `LIMITED` cuando falta autenticación o el proveedor no ofrece esa métrica.
- Un thread vacío no es una sesión durable. El orquestador futuro no debe persistir su
  ID como recuperable hasta confirmar el primer rollout/turno.
- La concurrencia live y la cancelación live requieren un `CODEX_HOME` autenticado
  específicamente para pruebas. Permanecen como validaciones posteriores para evitar
  consumo innecesario durante M00.
- La clasificación por texto es solo telemetría provisional. El futuro adaptador debe
  priorizar códigos estructurados de `turn.error` y RPC y conservar errores desconocidos.
- App Server sigue apareciendo como experimental en la ayuda de 0.163.0; se debe fijar
  y registrar la versión y generar/comparar su esquema al actualizar.

## Riesgos técnicos

- cambios incompatibles del protocolo entre versiones de Codex;
- identidad, routing y OAuth no necesariamente portables copiando archivos entre homes;
- límites compartidos por cuenta y métricas no disponibles con API key solamente;
- efectos parciales antes de un turno fallido o cancelado;
- falsa sensación de persistencia si solo se conserva el ID de `thread/start`;
- interferencia si se ejecutan pruebas contra el home habitual, expresamente prohibido.

## Criterios de aceptación

- [x] Cliente Python que inicia App Server y usa el protocolo oficial.
- [x] Creación de threads y recepción de respuestas/eventos demostradas.
- [x] Recuperación y reanudación cubiertas de forma reproducible.
- [x] Persistencia tras reinicio demostrada con un turno real completado.
- [x] Aislamiento por `CODEX_HOME` implementado y comprobado localmente.
- [x] Pruebas automatizadas y reales opt-in separadas.
- [x] Límites, cancelación y errores implementados/cubiertos sin carga innecesaria.
- [x] Resultados observados distinguidos de capacidades documentadas o pendientes.

M00 se declara completado. No bloquean M01, pero deben convertirse en pruebas o tareas
de hitos posteriores:

- validación live de concurrencia entre sesiones;
- validación live de cancelación y estado final;
- comportamiento de límites bajo los distintos métodos de autenticación;
- recuperación ante credenciales caducadas o revocadas;
- compatibilidad de access tokens según tipo de cuenta y versión de Codex.
