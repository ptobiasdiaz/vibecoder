# M03.3 — Workspaces Git aislados y generación inicial

Estado: **COMPLETADO; FLUJO LIVE VALIDADO**  
Fecha: 29 de octubre de 2026

## Objetivo y alcance

M03.3 transforma una especificación de bootstrap aprobada en archivos y un commit
local dentro de un workspace aislado. Reutiliza tareas, intentos y el adaptador Codex
de M02. No publica ramas, crea Pull Requests, hace merge ni modifica GitHub.

## Arquitectura

```text
GenerationService
  ├─ aprobación M03.2 + SHA-256 de especificación
  ├─ WorkspaceManager + GitAdapter
  ├─ InstructionLoader / DocumentResolver
  ├─ LocalWorker -> CodexAppServerExecutor
  ├─ GeneratedFilesValidator
  └─ SQLite generation_workflows
```

El adaptador Git usa `subprocess` con argumentos separados, nunca una shell. Se eligió
el binario Git frente a GitPython/pygit2 para conservar semántica nativa, soportar
repositorios vacíos y evitar una dependencia adicional. `git` es requisito operativo.

## Autorización y persistencia

`prepare` exige `BootstrapStatus.APPROVED`, actor, evento, especificación congelada y,
para generaciones nuevas, una configuración Git aprobada. Persiste sus ID/hash, usa
su rama bootstrap sin asumir `main` y rechaza cambios posteriores. La migración
`0005_initial_generation.sql` registra proyecto, bootstrap, repositorio, aprobación,
workspace, remoto, rama y commit base, tarea, sesión, versiones de instrucciones,
validación y commit final.

Las generaciones anteriores a M03.3.1 conservan workspace y commit. `legacy-check`
indica que necesitan una aprobación nueva antes de cualquier efecto remoto.

Estados:

```text
PREPARING_WORKSPACE -> PENDING -> GENERATING -> VALIDATING -> READY_TO_PUBLISH
                               \-> BLOCKED / FAILED
READY_TO_PUBLISH / BLOCKED / FAILED -> ARCHIVED
```

Una interrupción en `GENERATING` usa la recuperación conservadora de M02. Un intento
indeterminado deja la generación `BLOCKED`, conserva archivos e identificadores y no
reenvía el prompt. `VALIDATING` puede reconciliarse inspeccionando el filesystem real.

## Workspaces y Git

Cada ruta es `<workspace-root>/<project-uuid>`. La raíz debe estar fuera del checkout
de vibecoder. Se rechazan IDs inválidos, traversal, enlaces simbólicos, remoto distinto
y rama activa inconsistente. El token GitHub no se copia ni se pasa a Codex.

Con historia se detecta `origin/HEAD`, después `main`/`master` o una única rama. La
rama local usa `vibecoder/bootstrap-<id>`. Desde M03.4, una generación nueva sobre un
remoto vacío crea primero un commit raíz técnico vacío y reproducible en la rama
principal aprobada; la rama bootstrap y el contenido generado descienden de él. Todo
permanece exclusivamente local hasta que el publicador M03.4 actúa.

Las generaciones históricas cuyo código era el commit raíz se conservan sin reescribir
y requieren regeneración o reconciliación humana antes de publicar.

La limpieza es explícita y recuperable: mueve el workspace finalizado o bloqueado a
`.archive`; no borra trabajo.

## `.vibecoder/`, `doc/` y AGENTS.md

- `AGENTS.md`: reglas globales del proyecto; excepción deliberada en la raíz por
  compatibilidad con Codex.
- `.vibecoder/agents/main/AGENTS.md`: instrucciones específicas del principal.
- `.vibecoder/`: contexto operativo, memoria y workflows internos versionados.
- `doc/`: arquitectura pública, instalación, APIs y guías.

No se crean especialistas ficticios ni directorios vacíos. La generación recibe la
especificación aprobada e instrucciones para crear solo estructura necesaria.

La resolución `CONTEXT` busca primero `.vibecoder/` y después `doc/`. Las categorías
`INTERNAL`, `PUBLIC` y `AGENT_INSTRUCTIONS` no son intercambiables. Las escrituras
siempre indican destino y no tienen fallback ni sobrescritura implícita.

La jerarquía efectiva es seguridad del orquestador, reglas globales, instrucciones
específicas, contexto/memoria y tarea. Las específicas se cargan explícitamente; el
texto global no se duplica en el prompt porque Codex lo descubre desde el `cwd`. Se
guardan hashes SHA-256 de las instrucciones existentes antes de ejecutar y de las
generadas al validar. Conflictos declarados como `- Rule: clave = valor` bloquean el
contexto si los valores difieren.

## Integración Codex

La tarea `INITIAL_PROJECT_GENERATION` usa `LocalWorker.run_task`. Se crea una sesión
operativa separada vinculada al mismo agente principal, porque el thread conversacional
de M03.2 nació con otro directorio de trabajo. El runtime se deriva de la cuenta pero
reemplaza `cwd` por el workspace. App Server usa `workspace-write` y approval `never`.

El prompt contiene la especificación inmutable, aprobación, hash, separación
documental y prohibiciones de efectos externos. No se crea un segundo motor.

## Validación y commit

Antes del commit se inspecciona Git, no el texto de respuesta de Codex. Se exige:

- cambios reales y rama registrada;
- `AGENTS.md` y `.vibecoder/agents/main/AGENTS.md` no vacíos;
- rutas confinadas y enlaces seguros;
- tamaño máximo predeterminado de 2 MiB por archivo;
- ausencia de nombres sensibles, claves privadas y patrones conocidos de tokens;
- advertencias ante documentación aparentemente pública bajo `.vibecoder/`.

Un fallo conserva los archivos y bloquea publicación. Tras validación se añade solo el
árbol del workspace, se crea un commit sin firma en la rama bootstrap y se persiste el
hash. Repetir la operación verifica el mismo HEAD y no crea otro commit.

No se ejecutan scripts ni tests generados.

## CLI

```bash
python3 -m vibecoder.generation \
  --database /ruta/vibecoder.sqlite3 \
  --workspace-root /ruta/fuera/de/vibecoder/workspaces \
  prepare PROJECT_ID

python3 -m vibecoder.generation \
  --database /ruta/vibecoder.sqlite3 \
  --workspace-root /ruta/fuera/de/vibecoder/workspaces \
  --accounts /ruta/accounts.json \
  generate GENERATION_ID
```

Consultas y recuperación:

```bash
python3 -m vibecoder.generation ... status PROJECT_ID
python3 -m vibecoder.generation ... inspect GENERATION_ID
python3 -m vibecoder.generation ... recover GENERATION_ID
python3 -m vibecoder.generation ... archive GENERATION_ID
```

### Resultado live observado

El 29 de octubre de 2026 se ejecutó correctamente el flujo manual contra el proyecto
de prueba aprobado. Se confirmó la preparación del workspace desde el repositorio
registrado, la recuperación de la especificación congelada, la generación real con
Codex, la validación de la estructura, la creación del commit exclusivamente local y
la recuperación del mismo estado tras reabrir la persistencia. No se realizó push, no
se publicó ninguna rama y no se creó un Pull Request.

No se ejecutó esta prueba durante la implementación.

## Limitaciones

- un worker y una generación por proyecto;
- no hay lock distribuido, daemon, contenedor ni sandbox de SO fuerte;
- detección de secretos y conflictos semánticos necesariamente conservadora;
- no se ejecutan tests generados;
- M03.3 no hace push, PR ni merge; esas operaciones pertenecen a M03.4;
- generaciones históricas sin base técnica común no se publican automáticamente.

## Criterios de aceptación

- [x] Aprobación verificable y especificación congelada con hash.
- [x] Workspaces aislados para repositorios con historia o vacíos.
- [x] Rama bootstrap y primer commit local sin efectos remotos.
- [x] Generación mediante el worker M02 y sesión operativa separada.
- [x] Convención `.vibecoder/`, `doc/` y jerarquía `AGENTS.md`.
- [x] Resolución documental, hashes y conflictos explícitos.
- [x] Validación real del filesystem/Git antes del commit.
- [x] Persistencia, recuperación conservadora e idempotencia.
- [x] Pruebas automatizadas sin red, credenciales ni inferencia.
- [x] Validación live opt-in del flujo local completo.
